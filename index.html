RiseClient 1.8.9 — Java Tarafı Protokol Notları

RiseClient 1.8.9 (MCP 918 tabanlı) istemcisinin CraftRise oyun sunucularıyla nasıl konuştuğuna dair Java tarafındaki tespitler. Notlar, JAR'ın statik analizi ve trafiğin PCAP kaydından çıkarıldı. Amaç, protokolün kendisini anlamak; bir şey klonlamak değil.

Tamamen eğitim ve araştırma amaçlıdır. Burada anlatılanlar sadece protokolün Java katmanına dair notlardır. Ne bir bypass rehberi, ne bir launcher klonlama kılavuzudur. Tüm buradaki bilgiler public olarak yayınlanmış istemcinin statik analizinden elde edildi. Bu belgenin CraftRise'ın Kullanım Şartları'na aykırı herhangi bir amaçla kullanılması tavsiye edilmez, kullananların sorumluluğu kendine aittir. Yazar sadece dokümantasyon paylaşıyor.

01 — Giriş #

Bu döküman, RiseClient 1.8.9 (MCP 918 tabanlı Minecraft istemcisi) ile CraftRise sunucuları arasında geçen ağ trafiğinin ve JAR'ın içinde bulunan protokol katmanlarının notlarıdır. İstemci; obfuscated sınıflar, katmanlı AES şifreleme, base64 katmanları, Netty tabanlı özel bir JSON kanal protokolü ve genişletilmiş bir Minecraft handshake paketi kullanır. Aşağıda tüm bu parçalar tek tek açılıp deobfuscate edilmiş halleriyle verilmiştir.

Belge iki temel amaç için hazırlandı: (1) protokolü anlamak isteyen bir okuyucunun yalnızca bu sayfayı okuyarak akışı zihninde canlandırabilmesi, (2) bu HTML doğrudan bir dil modeline verildiğinde, modelin isim/alan/algoritma seviyesinde tam bir bağlam elde edebilmesi. Bu yüzden anahtar değerleri, sabitler, JSON şablonları ve wire format tabloları olabildiğince açık verilmiştir.

4.1 İstek Payload'u

Kısa ömürlü bir TCP bağlantısı üzerinden gönderilir; cevap alındıktan sonra sunucu bağlantıyı kapatır.

4.2 Hash Zinciri

→key = b64( AES( DEFAULT, AES( DEFAULT, b64( username + "###" + md5(password) + "###" + millis ) ) ) )
→sum = md5(key)
→sumBig = md5( sum + username + "....." )
→sumBigX = md5( "......" + sumBig + "......" )
→sumBigY = md5( "craftrise#" + username )

05 — Kalıcı Session Kanalları #

tryLogin cevabı alındıktan sonra istemci yeni bir TCP bağlantısı açar ve oturum boyunca açık tutar. Bu bağlantı olmadan oyun sunucusu C00Handshake'i reddeder — buraya dikkat.

5.1 Introduction Mesajı

Yeni açılan packet channel'a ilk gönderilen mesaj. packetContent içindeki fake_<random>:0 alanları anti-debug amaçlı gürültüdür; sunucu tarafından okunmaz.

JSON 
{
  "messageType": "packet",
  "packetContent": "{\"fake_60894048\":0,\"data\":\"{\\\"init\\\":true,\\\"password\\\":\\\"<PASSWORD>\\\",\\\"username\\\":\\\"<USERNAME>\\\"}\",\"fake_82729880\":0,\"fake_99858660\":0,\"channel\":\"introduction\",\"fake_59855487\":0,\"fake_21228190\":0,\"fake_79391757\":0,\"fake_38971509\":0,\"fake_53608396\":0,\"fake_91197214\":0,\"fake_62827185\":0,\"fake_9946018\":0}",
  "packetName": "PacketRequest"
}

5.2 Diğer Mesajlar

JSON 
{"messageType":"getAvailableLobby","playerName":"<username>"}
{"messageType":"getHashsCrypted","playerName":"<username>"}
{"messageType":"alive"}
Introduction + getAvailableLobby + getHashsCrypted mesajları channel açıldığında tek seferde gönderilir, ardından her 3 saniyede bir polling yapılır. alive keepalive ise oyun sunucusunun 4754 portundaki ayrı bağlantıda her 5 saniyede bir gönderilir.

5.3 Wire Format (Netty ObjectEncoder)

Binary Format 
[4 byte big-endian length] [0x05 STREAM_VERSION] [0x74 TC_STRING]
[2 byte UTF length] [UTF-8 bytes of JSON]

Örnek — {"messageType":"alive"} (23 karakter) için üretilen 31 byte:

00 00 00 1b # length = 27
05 # STREAM_VERSION
74 # TC_STRING
00 17 # UTF length = 23
7b 22 6d 65 73 73 61 67 65 54 79 70 65 22 3a 22 61 6c 69 76 65 22 7d # {"messageType":"alive"}

06 — Genişletilmiş C00Handshake #

Standart Minecraft 1.8 C00Handshake paketine iki ek String alanı eklenmiş:

Packet Structure 
VarInt(protocolVersion = 47)
String(serverAddress)      ← blob JSON'daki serverAddress ile birebir aynı
Short(port)                ← blob JSON'daki port ile birebir aynı
VarInt(nextState = 2 LOGIN)
String(handshakeBlob)      ← {"1":"<encBlob>","2":"<blobHash>"}
String(passwordToken)      ← base64(password)

Hemen ardından standart C00PacketLoginStart paketi gönderilir.

08 — nameHash Algoritması #

Bytecode'da doğrulandı. Method içindeki iload_2, iconst_1, iadd sırası, port değerini 1 arttırıyor:

Algorithm 
plaintext = username + clientHash + String.valueOf(port + 1) + serverAddress
nameHash  = base64( AES_ECB(NAMEHASH_KEY, plaintext) )
port + 1: Blob'daki port alanının bir fazlası kullanılır (bytecode'daki iconst_1, iadd sırasından geliyor). Küçük ama gözden kaçtığında blob'u geçersiz kılan bir detay.

clientHash: Yüklü RiseClient JAR'ının SHA-1'idir — decompile edilmiş versiyon değil, orijinal encrypted versiyonun hash'i.

Örnek — username=Player123, clientHash=2177d15e..., port=3007, serverAddress=185.255.92.10

Örnek Plaintext 
Player1232177d15e451be7c585382bf79c9bbbd6b27725a230081853.255.92.10

09 — racGuardKey Placeholder Çözümü #

Blob içindeki racGuardKey alanı map'e ilk yazıldığında değeri "%RAC_GUARD_KEY%" literalidir. Şifrelemeden hemen önce String.replaceAll("%RAC_GUARD_KEY%", <gerçek_değer>) çağrısıyla değiştirilir.

Gerçek değer JAR'da 64 elemanlı bir long[] dizisinde şifreli saklanır. Deobfuscate adımları:

1Long dizisi (64 eleman)
↓
2Her element için: byte = (long - 7) / 9000
↓
3byte[64] → String → base64 decode → 48 byte ciphertext
↓
4AES_DECRYPT( DEFAULT ) → "UVVCRU5aMTEzNlp5ZWZISkIyMTNCVjIxSEFCbnNm" (40 byte)
↓
5base64 decode → "QUBENZ1136ZyefHJB213BV21HABnsf" (30 byte)
Bu adımların çıktısı: QUBENZ1136ZyefHJB213BV21HABnsf. Placeholder yerine bu 30 byte'lık string doğrudan kullanılır.

12 — String Obfuscation #

crsecond/Ͻ sınıfındaki string sabitleri runtime'da decrypt ediliyor. Şema:

Algoritma
DES/CBC/PKCS5Padding, IV = zero
Base field
f = 98049190020208 (static long)
Her metot
var3 = f ^ method_xor_const
Her invokedynamic
actual_long = CP_LONG ^ var3
h[] index
h_index = sipush ^ (actual_long & 0x7FFF) ^ 22253
DES key
actual_long'un 8 byte'lık serialization'ı

Bu formülle Ͻ.h array'inden istenen decrypted string offline olarak çıkarılabilir.

14 — Session Kanallarının Önemi #

Oyun sunucusu C00Handshake'i kabul etmek için aynı IP adresinden aktif paralel session kanalları bekler. Blob'un doğru yapıya sahip olması tek başına yetmiyor — kanalların aktif olması ve keepalive'ın atılıyor olması da şart.

Pratik olarak: packet channel ve keepalive bağlantıları hazır değilse handshake reddedilir. İlk sırayı bozarsanız server graceful Disconnect gönderiyor.

16.2 Blob Şifreleme

Java 
static String encryptBlob(String jsonPayload) throws Exception {
    String b64Json   = base64(jsonPayload);
    String plaintext = BLOB_PREFIX + b64Json + BLOB_SUFFIX;
    String enc1      = base64(plaintext);
    String enc2      = base64(enc1);
    byte[] aes1      = aesEncryptBytes(enc2.getBytes(UTF_8), AES_KEY_INNER);
    String b64Aes1   = base64(aes1);
    byte[] aes2      = aesEncryptBytes(b64Aes1.getBytes(UTF_8), AES_KEY_OUTER);
    return base64(aes2);
}

17 — Ek Notlar #

  • Blob JSON alan sırası server tarafında önemsizdir (HashMap serialization).
  • val2 için ilk bakışta md5(keyValidator_uuid) gibi görünse de doğru formül md5(base64(AES(SESSION, val1))).
  • Oyun sunucusu portu dinamiktir: getAvailableLobby cevabından okunması şart.
  • Blob'daki serverAddress ve port de dinamiktir; blob içindeki değerler kullanılan gerçek target ile birebir uyumlu olmalıdır.
  • nameHash içindeki port + 1 küçük ama kritik bir detay — bytecode'daki iconst_1, iadd sırasına dikkat.
  • runtime nested objesi sadece 6 rac-* alanı içermelidir. Ek donanım alanları eklemek blob'u geçersiz kılar.
  • Bu belge deliberately Java katmanının notlarıyla sınırlıdır — istemcinin çalışması için var olan diğer bileşenler (native modüller vs.) kapsam dışı.
Tekrar hatırlatma: Bu döküman tamamen eğitim ve reverse engineering çalışması amacıyla yazılmıştır. İçerik CraftRise'a saldırmak, sunucularına yetkisiz erişmek veya ToS'u ihlal etmek için değildir. Yazar sadece protokolün nasıl işlediğini belgeleyip paylaşıyor; kullanım tamamen okuyucunun sorumluluğundadır.
